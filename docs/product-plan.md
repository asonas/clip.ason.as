# clip.ason.as — テキストと画像を集める、AT Protocol上のクリップ帳

2026-10-28 / レビュー用の初案。アカウント作成・DNS変更・実装・デプロイはまだ行わない。

## 作りたいもの

気になった文章や画像を、自分の短いコメントとともに気軽に残す。clip.ason.asを開くと、集めてきたものがTumblrのように流れて見える。個々のクリップはAT Protocolの公開データとして保存し、自分のサイト以外からも利用できるようにする。

ユーザーからの要件は、clip.ason.asというアカウント、テキストと画像のクリップ、Tumblrのような体験、AT Protocolでの配信。以下の具体案は提案であり、まだ採用決定ではない。

投稿者はasonas本人だけ。誰でも閲覧できる個人サービスとして作る。下書き機能は設けず、投稿すると公開され、公開後に更新できる。PDSは自前で運用する。これらは第1回レビューで確認済み。

## 使う体験

### 集める

**投稿の入口はChrome拡張にする。** ページ上の文章を選択して右クリックからクリップする、画像を右クリックして取り込む、拡張ボタンから文章や画像を入力する。ページのURLとタイトルを出典として添え、投稿前に確認・修正できる。タイトルは必須にせず、画像だけ、文章だけでも投稿できる。

引用文と自分のコメントは別の入力欄にする。たとえば、記事の一節を引用欄へ貼り、下に「この考え方を覚えておきたい」と書く。表示でも引用と自分の言葉を区別する。

初版からChrome拡張を作り、Web管理画面は公開済みクリップの編集・削除を担当する。ページ全体の自動収集とスマートフォンの共有シートは後の検討にする。

拡張はManifest V3を使い、選択テキスト・画像のコンテキストメニューと、確認・投稿用のサイドパネルを用意する。`activeTab`等を用い、ユーザーが操作したページを対象にする。画像が別ドメインにある場合は必要なhost permissionを個別に取得するか、画像の貼り付けに切り替える。`activeTab`だけであらゆる画像を取得できるとは扱わない。[19]

認証は拡張からWebの本人認証へ誘導し、アプリAPIに対する期限付きの認証を拡張へ渡す案とする。PDSのパスワードや署名鍵は拡張に埋め込まない。Web側OAuthとの連携、拡張IDに紐づいたリダイレクト、ワンタイムコードの検証は接続試作で確認する。

拡張のservice workerは常駐しないため、投稿を受理したあとの処理はサーバーが引き受ける。拡張を閉じてもジョブIDで結果を確認でき、再試行で二重投稿しない。これは下書き機能ではなく送信処理の継続である。[20]

### 残す

入力して「投稿」を押すとAT Protocolへ公開する。下書き一覧や下書き保存は設けない。送信前はフォーム上で画像、引用、コメント、出典を確認でき、公開後も編集・削除できる。送信失敗時は入力を画面に残して再試行できるようにする。

「公開データとして保存できた」と「clip.ason.asに反映できた」を別々に管理する。表示側だけ失敗したときに、公開ボタンの再実行で投稿が二つできないようにする。

### 眺める

トップは新しい順のフィード。文章は余白と文字で、画像は画像そのものを大きく見せる。装飾やカード枠より、集めた内容を主役にする。

| 画面 | 初版の内容 |
|---|---|
| `/` | テキストと画像が混ざるフィード。日付・出典・タグを添える |
| `/clips/<rkey>` | 一件の固定URL。本文、画像、出典、自分のコメント |
| `/tags/<tag>` | 同じタグのクリップ一覧 |
| `/archive` | 月ごとに辿れる一覧 |
| `/admin` | 本人だけの公開済み一覧、作成と編集 |

画面の見た目とレイアウトは後日Figmaで検討する。一列・複数列などはこの文書では決めない。JavaScriptを実行しなくても公開内容と次ページへのリンクを読めることは、配信上の要件として残す。

Tumblrの「形式に縛られず投稿できる」「個人の好みが蓄積する」を取り入れる。フォローする相手のダッシュボード、リブログ、いいね、コメント、動画・音声は初版に含めない。

## アカウントとデータの持ち方

**clip.ason.asをWebサイトのURLとAT Protocolのハンドルに使い、専用DIDを一つ作る。** 既存の個人アカウントとは分ける提案。

ハンドルとWebサイトは同じドメインでもよい。DNSの`_atproto.clip.ason.as`にDIDを示すTXTレコードを設定し、DID側にもハンドルを登録して双方向に確認する。Webサイトの配信先とPDSの配信先は独立している。[1]

初案では`did:plc`を推奨する。ドメインを名前として使うために`did:web`を選ぶ必要はない。`did:web`ではドメインを失うと同じ識別子を維持できないため、紹介記事の選択をそのまま引き継がない。[2]

### PDSをどこに置くか

PDSは自前で運用する。第3回レビューで、既にCloudflare Workers Paidを契約していることを確認した。紹介記事と同じく、**Cloudflare上でPDSとクリップアプリを運用する方針を第一候補**にする。NASとの比較は判断の根拠として残す。

**Cloudflareの既存契約を使い、まずCirrusでPDSの接続・公開・復元を検証する案を推奨する。** 新たなVMの固定費と自宅の停電・回線依存を避けられる。紹介記事の「Workersで処理、クラウドの永続ストレージへ原本、WebSocketでRelayへ配信」という分担を参考にする。ただし記事のdirigをそのまま使えるとは確認できていないため、導入可能な既存実装から検証する。PDSのドメインは`pds.clip.ason.as`を仮置きする。[3][16]

PDSはレコードの保存だけでなく、署名付きリポジトリ、認証、blob管理、Relayが購読するWebSocketのイベント配信を担う。標準PDSのコンテナをLambdaに置くだけでは、この常駐プロセスと永続データを扱えない。

| AWSでの案 | 評価 |
|---|---|
| アプリはLambda・DSQL・S3、PDSはEC2＋永続ディスク | 技術的な候補だが、VMの固定費を避けるため現在は保留 |
| PDSもLambda・DSQL・S3を中心に実装 | 検証候補。ストレージ層、イベント配信、認証などの移植・実装が必要になり、PDS自体を作るプロジェクトになる |

通常のLambda Event Functionには実行時間の上限があり、API Gateway WebSocketにも接続時間・フレームサイズ等の制約がある。WebSocketを別サービスに分けるだけでAT Protocolのバイナリイベント配信が成立すると仮定せず、Relayとの実接続で検証する。[9][10]

DSQLはアプリの公開コピーや処理状態には候補になるが、既存PDSのデータベースを設定変更だけで置換できるとは扱わない。使用SQL・トランザクションとDSQLの対応範囲を確認する必要がある。[11]

### PDSは常時起動が必要か

**外部からいつでもアクセスできる必要はあるが、CPUを常時動かして課金され続けることがプロトコルの要件ではない。** 公式PDSを使うなら、プロセスを常時稼働させる構成が基本となる。投稿時だけ起動する運用では、外部からのレコード・画像取得、OAuth、Relayとの同期がその間使えない。既に外部へ複製された投稿は、PDS停止だけで必ず消えるわけではない。[6][8]

Cloudflare向けの実装は、WorkersとDurable Objectsで必要時に処理できる。Hibernation対応のWebSocketなら、接続を保ったまま待機中のDO実行時間の課金を止められる。ただし採用PDSがそのAPIを使い、タイマー等で休眠を妨げないことを確認する。Cloudflareに置けば無条件で待機費用がゼロ、という意味ではない。[12]

### NASとCloudflareの比較

| 判断軸 | NAS＋Coolify＋公式PDS | Cloudflare＋Cirrus |
|---|---|---|
| 常駐VMの追加契約 | 不要。既存NASでコンテナを常時稼働 | 不要。Workers＋DO＋R2 |
| PDS実装 | 公式の配布コンテナを利用 | 単一ユーザー向けのコミュニティ実装。作者はexperimental betaと明記 |
| 追加費用 | 増分の電気代、外部バックアップ、必要なら公開配信費 | Free枠内なら対象利用料$0も可能。Paidはアカウント単位で最低$5/月＋超過分 |
| 画像原本 | NASの永続領域。外部バックアップが必要 | R2。保存量と操作回数で課金、インターネットへの転送は無料 |
| 停電・回線断 | 新規投稿・PDS読み取り・同期が止まる | 自宅の停電・回線から独立 |
| 更新と復旧 | コンテナ更新、DBの整合したバックアップと復元 | Workersの更新、DO/R2と鍵のバックアップ・移行 |
| 採用前の確認 | Coolifyの公開経路と永続領域、Relay再接続 | OAuth、独自レコード、Bluesky、did:plc、移行、休眠動作 |

Cloudflareで動くPDSは自作するしかない、ということではなかった。調査で見つかった[Cirrus](https://github.com/ascorbic/cirrus)はWorkers＋SQLite-backed Durable Object＋R2を使い、レコード操作、firehose、OAuth、移行を実装している。一方、実験的ベータで破壊的変更の可能性が明記されている。通常の新規アカウント作成APIはなく所有者をデプロイ時に設定する方式で、did:plcについては既存アカウントからの移行が案内されている。今回の新規専用DIDをどう用意するかは採用前の確認点。[16]

紹介記事のdirigのページからは再利用できるソースや導入手順を確認できなかったため、導入可能な候補として確定していない。

### 費用の目安と条件

2026-10-28時点の公式価格。税・為替換算・既存契約の消費分は含めない。実測利用量に基づく請求予測ではなく、判断用の条件付き試算。

- **NAS**：セルフホストCoolifyのライセンス料は$0。既にNASを24時間稼働させているなら、比較するのはNAS全体の電気代ではなく追加負荷分。仮に増分5W、30日、電力単価31円/kWhなら約112円/月、10Wなら約223円/月。ワット数・単価は仮定であり実測ではない。バックアップ費は別。[17]
- **Cloudflare Free**：SQLite-backed DOはFreeプランでも利用できる。ただし日次上限を超えると処理が失敗するため、無料で運用できるかはCPU・DB・イベント配信を試して判断する。R2の有効化も必要。[13][16]
- **Cloudflare Paid（現在の契約）**：ユーザー確認により契約済み。最低$5/月は既存アカウントの基本料なので、このサービスのために追加でもう$5払う前提ではない。DOは月100万リクエスト・400,000 GB-sが含まれる。参考として128MB相当のDO一つが30日間ずっとアクティブでも331,776 GB-sであり、その時間だけなら枠内。ただし同一アカウントの他のDO・要求数・ストレージは合算される。現在の枠の残量は未確認なので、追加利用料が$0とはまだ断定しない。[13][14]
- **R2 Standard**：月10 GB-month、Class A 100万回、Class B 1,000万回まで無料枠。超過保存料は$0.015/GB-month。仮に画像原本と表示コピーの合計が月平均20GBで、操作が枠内なら保存料は$0.15/月。画像変換サービスや別のバックアップ先の料金は含まない。[15]

既存Paid契約を利用できるため、今回の比較は「Cloudflareの新規基本料対NASの電気代」ではなく、**Cloudflareの追加使用量と実装の保守負担対、NASの増分費用と自宅稼働への依存**になる。これを踏まえ、Cloudflareを第一候補へ変更する。NAS＋公式PDSはCirrusの互換性・復旧要件が満たせなかった場合の代替案とし、最初から両方を構築しない。

Cloudflare採用の確認点は、専用did:plcの作成または移入、独自クリップと画像の公開・更新・削除、OAuth、Blueskyへの試験配信、Relayの再接続、repo・blob・鍵からの復元。これに既存アカウントの使用量確認を加える。検証を通ればCloudflareで進め、通らない点があればその不足だけを評価する。

### NASの現在の状態と導入条件

2026-10-28 18:43 JSTに`ssh nas`で読み取り確認した。x86_64、メモリ31GiB中available約9.2GiB、`/mnt/data`に約7.2TiBの空き、Coolifyはhealthy、cloudflaredはactiveだった。負荷平均は0.47 / 0.75 / 0.86。これは一時点の状態で、追加サービスの継続稼働を保証するものではない。

公式PDSの案内は1〜20ユーザー向けに1 CPU・1GB RAM・20GB SSDを目安としている。現在の空きからは単一アカウントを検証する余地がある。ただし`/mnt/data`の空き容量はSSD性能の確認ではないため、repo用SQLiteの置き場は別途確認する。[8]

CoolifyのDocker Composeで公式PDSコンテナを配置し、データ用の永続領域を割り当てる。公式インストーラーをそのままNASへ実行して既存のリバースプロキシを書き換える方法は取らない。CoolifyのプロキシまたはCloudflare TunnelでHTTPSとWebSocketを公開し、PDSの公開APIには対話ログイン必須のAccess制限をかけない。管理画面は別に保護する。[18]

確認するのは、TLS、blobアップロード、`subscribeRepos`の継続接続と再接続、再起動後の永続性、整合したDBバックアップと別ホストへの復元。NASが止まっても公開サイトを読めるよう、生成済みHTMLと縮小画像はクラウドに置く案が有効。NAS停止中の新規投稿は成功扱いにせず、拡張に状態を返す。

## AT Protocolに何を保存するか

公開したクリップの原本はPDSに置く。サイト側のDBは、一覧・タグ・表示を速くするための再構築可能なコピーと、公開処理の状態を保持する。認証情報と処理途中の入力は公開データから分け、下書きとして閲覧・管理する機能は作らない。

独自Lexiconの仮名は`as.ason.clip.entry`。公開前に既存のクリップ／ブックマーク向けLexiconと比較し、要件を満たすものがあれば採用する。現段階で既存アプリとの互換性は約束しない。

### レコードの案

| フィールド | 意味 |
|---|---|
| `$type` | `as.ason.clip.entry`（仮） |
| `text` | 自分の文章・コメント。初版はプレーンテキスト |
| `quote` | クリップした引用文。自分の文章と分ける |
| `source` | 出典URL、任意のタイトル・著者名 |
| `images` | blob参照、代替テキスト、幅・高さ。必要なら画像ごとの出典 |
| `tags` | 整理用のタグ |
| `createdAt` | 初回公開日時 |
| `updatedAt` | 最終更新日時 |

文章・引用・画像のうち少なくとも一つを必須にする。画像は初版で最大4枚を仮置きし、容量上限は採用PDSと画像処理の検証後に確定する。これはAT Protocol全体の上限ではない。

初回公開の前にrkeyを一度採番し、公開処理の再試行でも同じ値を使う。編集では同じrkeyのレコードを更新し、AT URIとWebの固定URLを維持する。レコードの内容が変わればCIDは変わる。[4]

画像は先にPDSへアップロードし、返されたblob参照をレコードに含める。公開表示用の画像は別途縮小してCDNから配信する。PDSから毎回原寸を読み出す構成にはしない。[5]

## 「配信する」の範囲

**独自のクリップをAT Protocolへ公開することと、Blueskyのタイムラインに流すことは別の処理。** 独自Lexiconのレコードが自動でBlueskyの投稿になるわけではない。

| 配信先 | 実装案 | 初版での扱い |
|---|---|---|
| clip.ason.as | 自分のPDSからクリップを取り込み、Webとして表示 | 必須 |
| AT Protocol対応アプリ | 対応Lexiconのレコードを公開し、取り込める状態にする | 必須。ただし第三者アプリの対応は別途必要 |
| Bluesky | 同じ専用アカウントで`app.bsky.feed.post`を作り、クリップのリンクと短い紹介を投稿 | 試験的に配信する。投稿時の「Blueskyにも送る」で選択する案 |
| RSS | 公開クリップのフィードをサイトから提供 | 初版の提案 |
| Grain・Sembleなど | 各サービスのLexiconと受け入れ条件を個別に調査 | 初版では実装しない |

独自クリップを主とし、Blueskyへの紹介投稿も試す。クリップと紹介投稿のAT URIを対応づけ、紹介投稿だけ失敗した場合はそこだけ再試行する。初案では更新時に新規投稿を増やさず、紹介文を更新し、クリップの削除時は対応する紹介投稿も削除する。独自レコードと紹介投稿を一つのトランザクションとして扱わない。

## 実装構成の提案

weblogとは別アプリ・別リポジトリにし、公開・障害・データ管理を独立させる。以下はホスティング先を確定する前の構成案で、既存環境の再利用範囲は実装着手時に確認する。

```text
本人のChrome拡張
  │ OAuthでログイン、投稿・更新
  ▼
clip管理アプリ ── 画像と公開レコード ──▶ 専用アカウントのPDS
  │                                         │
  │ 公開後に取り込みを実行                    └─▶ Relay ─▶ 対応する外部アプリ
  ▼
表示用DB・縮小画像 ──▶ 公開HTML・CDN ──▶ clip.ason.as
  ▲
  └── 定期的に専用PDSと照合し、取りこぼしや外部編集を修復
```

初版は自分一人のデータだけを表示するため、全ネットワークのfirehoseを取り込まない。公開直後の取り込みと、専用アカウントの対象コレクションの定期照合から始める。初期データと削除の照合は全ページの取得成功を確認してから確定し、通信失敗を「レコードが消えた」と解釈しない。

Relayに登録・購読されていることは外部配信の確認項目にするが、自分のサイト表示をRelayの状態に依存させない。第三者アプリへ届くことを確認するには、そのアプリが理解する形式を選ぶ必要がある。[6]

### Cloudflareでのアプリ構成

Chrome拡張・管理画面・サーバーはTypeScriptとAT Protocol向けSDKを使う。第一候補はCloudflare。PDSはCirrusのWorker＋Durable Object＋R2、クリップアプリは別のWorker＋D1＋R2で構成する。PDSのrepoとアプリの表示DBは責務が違うため、記事と同じサービス名に揃えるためだけにPDSをD1へ書き換えない。

公開・画像処理の再試行にQueues、照合にCronを使う。公開HTMLと縮小画像はR2から配信し、エッジでキャッシュする。PDSとアプリを分けることで、公開サイトの変更がアカウントの原本管理に及ぼす影響を小さくする。以下のAWS・NAS構成は代替案として保持する。

| アプリ配置 | 構成案 |
|---|---|
| AWSを継続利用 | API Gateway＋Lambda、DSQL、S3＋CloudFront、SQS、EventBridge Scheduler。PDS用EC2は不要 |
| Cloudflareへ寄せる | Workers、D1、R2、Queues、Cron。PDSをCirrusにする場合も、そのDOと表示用DBを分ける |
| NASへ寄せる | Coolify上のアプリと永続DB。公開HTML・画像のクラウド配信を組み合わせれば閲覧を自宅障害から分離できる |

どの構成でも公開HTMLは投稿・更新時に生成し、閲覧ごとにDBを読まない。公開処理の重複実行はジョブIDとバージョンで制御する。鍵・OAuthセッションの暗号化とバックアップも設計に含める。

OAuthでログインしたDIDが専用アカウントと一致する場合だけ管理画面を許可する。ハンドル文字列だけで本人判定しない。OAuthのDPoPや更新処理は対応SDKに任せ、独自認証プロトコルを作らない。[7]

データは`publish_jobs`（公開・再試行）、`clips`（公開コピー）、`media`（表示画像の対応）を基本とする。下書きテーブルは作らない。処理の再試行に必要な入力は公開ジョブとして非公開で一時保持し、完了後は保持期限に従って消す。公開後にPDS側で直接編集された内容も取り込めるよう、表示DBの内容を原本としてPDSへ上書きしない。

### 公開・編集・削除の扱い

1. 投稿指示を公開ジョブとして受け付け、rkey（一件のクリップを区別するキー）を確定する。
2. 画像を検証・必要に応じて縮小し、公開する画像から位置情報などのメタデータを除いてPDSへ送る。
3. レコードを書き込む。応答が途切れた場合は同じrkeyを照会し、成功済みか確認する。
4. PDSのレコードを表示DBへ取り込み、画像を配信用に準備する。
5. 該当する詳細・一覧・タグ・RSSのキャッシュを更新する。
6. 「Blueskyにも送る」を選んだ場合、紹介投稿を作る。

編集は取得済みCIDを使った競合確認を行い、別クライアントの更新を黙って上書きしない。削除はPDSとサイトの両方へ反映し、失敗した工程だけ再試行する。公開後に外部へ複製されたデータを完全に回収することはできないため、公開前の確認画面でその性質がわかるようにする。

## 運用と負荷

公開フィードと詳細ページは、本文・画像・出典をHTMLに含める。一閲覧ごとにPDSや補助APIへ取りに行かない。更新のたびに必要な表示を更新し、閲覧はCDNで受ける構成にする。

費用の主な変数は画像の保存容量・配信量、PDSの利用料、アプリ実行環境。現段階では価格や削減額を仮定せず、PDS候補と月あたりの画像数・サイズを決めてから見積もる。

監視は公開処理の失敗数、PDSとサイトの反映遅延、画像配信量、HTMLのキャッシュヒット率を中心にする。PDSレコードとblob、アカウント復旧に必要な鍵をバックアップし、表示DBを失っても復元できることを確認する。サイト用画像コピーを原本のバックアップと取り違えない。

引用と画像には出典を残せるようにする。入力された本文は安全にエスケープし、画像は実データとサイズを検証する。URLのサーバー側自動取得は初版で行わず、後で実装する場合に内部ネットワークへのアクセスを防ぐ設計を含める。

## 実装の順序と完成条件

| 段階 | 作るもの | 確認すること |
|---|---|---|
| 1. 接続を確かめる | テストアカウントで画像と候補レコードを作成・取得・更新・削除 | 採用PDSで必要な形式と容量を扱える |
| 2. 一件を公開する | 専用アカウント、OAuth、Chrome拡張、固定URL | ページで選択した文章・画像を投稿するとPDSとサイトへ公開される |
| 3. クリップ帳にする | フィード、タグ、月別一覧、編集、削除、RSS | スマートフォンでも投稿と閲覧が快適 |
| 4. 失敗から復旧する | 再試行、照合、キャッシュ更新、バックアップ | 応答断で二重投稿せず、表示DBをPDSから再構築できる |
| 5. Bluesky配信を試す | 選択したクリップの紹介投稿 | 配信失敗がクリップ公開を巻き戻さず、再試行で重複しない |

実装の最初のゴールは「文章と画像を一件クリップし、PDSのレコードとclip.ason.asの両方で確認できること」。その後に日常的な使い勝手を整える。

## 第1回レビューで決まったことと、残る判断

- 投稿者は自分だけ。
- 下書きは作らない。投稿後の更新には対応する。
- 独自クリップを公開し、Blueskyへの配信も試す。
- 見た目は後日Figmaで検討する。
- PDSは自前で運用する。
- 投稿は初版からChrome拡張を使う（第2回レビュー）。
- Cloudflare Paidは契約済み。紹介記事に倣いCloudflare構成を優先する（第3回レビューの意向）。

次の設計はCloudflareを前提に詰める。Cirrusを採用できるかはテスト用の専用アカウントで検証し、互換性・復元と既存Paid枠の使用状況を確認する。NASは代替候補として残す。見た目は予定どおりFigmaで別途検討する。

アプリの内容への合意と、アカウント作成・本番配備の実行は区別する。

## 用語集

| 用語 | このサービスでの意味 |
|---|---|
| ハンドル | 人が読むアカウント名。`clip.ason.as`を使う |
| DID | 名前を変えてもアカウントを識別するためのID。`did:plc:...`を提案 |
| PDS | 自分の公開データと画像原本を保管し、他のサービスへ提供するサーバー |
| Repository / repo | 一つのアカウントが持つ公開レコードの集合。更新が署名される |
| Collection | 同じ種類のレコードをまとめる単位。クリップなら`as.ason.clip.entry`（仮） |
| Record | 一件のクリップに相当する構造化データ |
| rkey | Record Key。同じcollection内の一件を区別するキー。編集しても同じ値を使う |
| TID | 時刻をもとにした識別子の形式。新しいrkeyを作るために使うが、rkeyが常にTIDというわけではない |
| AT URI | `at://DID/collection/rkey`。誰の、どの種類の、どのデータかを示す住所 |
| CID | 内容から計算される識別子。本文や画像の内容が変わると変わる。固定の投稿IDとは別 |
| Lexicon | クリップにどの項目があるかなど、データやAPIの形式を定義する仕様 |
| NSID | Lexiconなどの名前。ドメインを逆順にした名前空間を使う |
| blob | 本文とは別に保存する画像などのバイナリデータ |
| Relay / firehose | PDSから更新を集める中継サーバーと、その更新の連続配信 |
| AppView | 公開データを取り込み、一覧や検索などをアプリへ提供する仕組み |
| OAuth | パスワードをアプリへ渡さず、アカウントへのアクセスを許可する認証・認可の仕組み |
| DSQL | AWSのデータベース。ここでは表示用コピーと処理状態の保存先 |

たとえば`at://did:plc:example/as.ason.clip.entry/3example`なら、`did:plc:example`が持ち主、`as.ason.clip.entry`が種類、`3example`がrkey。説明用の値であり、実在するレコードではない。
